커뮤니케이션



[관리자와 실무자의 잘못된 커뮤니케이션은 프로젝트 일정에 악영향을 미친다]

나는 Microsoft MVP 다.

이름은 거창하지만 사실 누군가 물어볼 때 잘 대답해주는 사람이라는 뜻이다.
그래서 항상 수 많은 사람들의 질문들을 헤집고 다니며 내가 대답해 줄 수 있는 것들을 찾곤 한다.

간혹 질문들 중에는 최초의 목적을 잊은 채 최종적인 결론만을 묻는 내용들을 볼 수 있다.
예를 들어 c:\ 에 있는 파일들의 목록을 얻고자 하는데 당장 생각나는게 도스 명령어 DIR 밖에 없다.
DIR 을 수행하면 도스창이 뜨면서 화면에 파일 목록이 출력되는데 이 화면에 출력되는걸 내가 가로채면 될것 같다.
그래서 질문하기를

"도스 화면을 내가 만든 프로그램에서 가로챌 수 있는 방법을 알려주세요"

얻을 수 있는 대답은 프로세스를 생성하면서 표준 IO 를 리디렉션하라는 내용일 것이다.
이건 마치 콩쥐가 부러진 호미로 밭을 갈고 있는걸 황소가 도와준다고 나서서 호미만 고치고 있는 격이다. 문제는 콩쥐가 '밭을 갈아줘' 라고 부탁한게 아니라 '호미가 망가져서 일을 할 수가 없어..' 라고 말한것이다. 황소탓은 아니다.

파일의 목록을 얻기 위해서는 findFile API 를 사용하면 된다.
원하는 경로의 파일들의 정보를 순차적으로 얻어올 수 있다.
이 해답을 얻기 위해서는 귀찮더라도 장황한 배경 설명이 필요하다.

"제가 c:\ 에 있는 파일 목록을 얻어와서 작업해야 하는데 도스 명령어 DIR 을 사용하려고 하거든요. DIR 을 실행시키는것 까지는 되는데 이게 화면에 출력되더라구요. 이걸 제 프로그램에서 읽어와서 분석하면 될것 같은데 무슨 방법이 없을까요?"

이렇게 질문했다면 반드시 이런 답변을 얻을 수 있다.

"파일 목록을 얻기 위해 도스의 DIR 명령을 사용하실 필요는 없습니다. findFile API 를 사용하시면 쉽게 원하는 경로의 파일 정보를 얻을 수 있습니다. 사용방법은... <후략>"

몰라서 묻는거니까 어디서부터 물어봐야 할지도 잘 모르는게 태반이다.
그렇다면 최대한 많이 알려주면 되는것 아닌가.

내가 질문글을 쓰는데 10분 더 투자하면 원하는 답변을 24시간 빨리 얻을 수 있다.
